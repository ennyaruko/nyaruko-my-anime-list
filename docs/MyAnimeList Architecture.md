# Архитектура приложения MyAnimeList

> **Статус:** предлагаемое архитектурное решение для MVP с учётом дальнейшего перехода к BFF/SSR  
> **Назначение:** единый источник правил для разработчика и ИИ-агентов  
> **Основной принцип:** структура кода должна отражать архитектурные границы из SAD и ADR, а не заставлять эти границы распределяться по слоям другой методологии.

## 1. Решение в кратком виде

Для проекта выбирается **модульная Clean/Hexagonal Architecture с отдельными слоями Presentation, Application, Domain и Infrastructure, а также явным Synchronization-компонентом**.

FSD не используется как главная архитектурная система проекта. При этом полезные приёмы FSD — организация UI по страницам, виджетам и пользовательским возможностям — можно применять **внутри Presentation Layer**, не распространяя FSD-слои на всё приложение.

Это решение принято по следующим причинам:

1. SAD уже определяет конкретные логические блоки и связи между ними.
2. Если пытаться представить каждый блок SAD через слои FSD, ответственность одного архитектурного блока может оказаться распределённой по нескольким FSD-слоям.
3. Такая раскладка повышает когнитивную нагрузку: разработчику и ИИ-агенту приходится восстанавливать границы системы по косвенным признакам.
4. Явные слои и правила зависимостей позволяют видеть, где заканчивается предметная модель, где выполняются сценарии приложения, где находится синхронизация, а где начинаются детали внешнего провайдера и хранения.
5. Структура должна поддерживать MVP без собственного backend и оставлять возможность переноса серверной части в BFF/SSR без переписывания доменной модели и контрактов приложения.

**Важно:** SAD и ADR определяют логические ответственности и архитектурные ограничения. Приведённая ниже файловая структура — конкретное проектное решение, принятое для того, чтобы эти ответственности были очевидны в коде. Не следует считать, что все названия каталогов дословно предписаны исходными документами.

## 2. Основания и связь с архитектурными документами

При реализации необходимо сохранять следующие решения из проектных документов.

### 2.1. SAD — Solution Architecture Document

SAD разделяет приложение на следующие логические ответственности:

- **Presentation Layer:** UI, страницы, компоненты и навигация.
- **Application Layer:** пользовательские сценарии, application services и контракты.
- **Domain Model:** внутренние сущности и бизнес-правила, не зависящие от внешнего API или хранения.
- **Synchronization:** координация синхронизации с провайдером, revalidation и разрешения конфликтов.
- **Provider Integration:** интеграция с внешним провайдером через контракт; преобразование provider DTO во внутреннюю модель.
- **TanStack Query / QueryClient:** runtime query cache и жизненный цикл server state.
- **Persistence:** сохранение выбранных категорий query state; в MVP — IndexedDB через persister.
- **Authentication:** OAuth и сессия, изолированные от доменной модели.

Эти ответственности не следует смешивать только потому, что в реализации они используют общие библиотеки или участвуют в одном пользовательском сценарии.

SAD также задаёт направление развития: в MVP основные части работают на клиенте, а при переходе к BFF/SSR отдельные части могут быть перенесены на сервер. Поэтому важны стабильные логические границы и контракты, а не текущая физическая локализация кода.

### 2.2. ADR-001 — Client-Side Architecture for MVP

MVP реализуется без собственного backend. Клиентская архитектура при этом должна учитывать возможный дальнейший переход к BFF/SSR. Отсутствие backend сейчас не означает, что бизнес-сценарии и провайдерскую интеграцию нужно без границ смешивать с UI.

### 2.3. ADR-002 — Provider-agnostic application model

Внутренняя модель приложения не должна зависеть от AniList или другого конкретного поставщика данных. Внешние DTO должны преобразовываться во внутреннюю модель на границе Provider Integration.

В результате домен и сценарии приложения работают с понятиями приложения, а не с типами ответов AniList GraphQL.

### 2.4. ADR-003 — AniList as the MVP data provider

AniList является провайдером MVP. Его API, GraphQL-операции, DTO, особенности статусов и OAuth относятся к интеграции с провайдером, а не к доменной модели.

### 2.5. ADR-004 — Server-State Cache, Persistence and Revalidation Strategy

TanStack Query / QueryClient владеет жизненным циклом runtime server-state cache. Synchronization не является владельцем query cache и не должен дублировать его обязанности.

Сохранение в persistence должно быть выборочным и соответствовать принятой политике. Query keys для пользовательских данных должны учитывать стабильный идентификатор пользователя. Service Worker не вводится как альтернативный владелец server-state cache, а полноценный offline mode не является целью MVP.

### 2.6. ADR-005 — Client-Side Persistent Storage

В MVP используется IndexedDB с TanStack Query persister, а не отдельная самодельная база данных приложения. OAuth token не сохраняется в query cache.

Категории данных имеют разные правила persistence. В частности, пользовательский список, справочные данные и просмотренные детали аниме могут сохраняться; поисковые результаты и исследовательские запросы по умолчанию не сохраняются; OAuth token не относится к persistence query cache. Пользовательские данные должны быть изолированы по user ID, а при logout пользовательские данные в кэше должны очищаться согласно принятой политике.

## 3. Архитектурная модель

### 3.1. Слои и компоненты

| Архитектурная ответственность | Предлагаемая область кода | Назначение |
|---|---|---|
| Presentation | `src/presentation/` | Страницы, виджеты, UI и обработка пользовательского взаимодействия |
| Application | `src/application/` | Сценарии приложения, orchestration и порты/контракты |
| Domain Model | `src/domain/` | Внутренние сущности, value objects и бизнес-правила |
| Synchronization | `src/synchronization/` | Координация синхронизации, revalidation и разрешения конфликтов |
| Provider Integration | `src/infrastructure/providers/` | Адаптеры провайдеров, DTO, внешние запросы и маппинг во внутреннюю модель |
| Query Cache | `src/infrastructure/query/` | Конфигурация и интеграционные механизмы TanStack Query |
| Persistence | `src/infrastructure/persistence/` | Persister и политика сохранения query state |
| Authentication mechanisms | `src/infrastructure/authentication/` | OAuth-детали и провайдерские механизмы аутентификации |
| Application bootstrap | `src/app/` | Запуск приложения, маршрутизация и подключение инфраструктуры |
| Общие технические примитивы | `src/shared/` | Небольшие действительно общие утилиты и технические абстракции |

`src/app/` — composition root: здесь приложение собирается из слоёв и подключаются реализации зависимостей. Сам по себе этот каталог не должен становиться местом для произвольной бизнес-логики.

`src/shared/` не является «слоем, куда можно положить всё». Здесь допустимы только общие технические элементы, у которых нет более подходящего владельца. Если код имеет явную предметную или архитектурную ответственность, он должен находиться в соответствующем слое.

### 3.2. Предлагаемая структура каталогов

Это целевая структура, а не требование создать каждый каталог заранее. Каталоги добавляются по мере появления соответствующей ответственности.

```text
src/
├── app/
│   ├── routing/
│   ├── providers/
│   └── bootstrap/
│
├── presentation/
│   ├── pages/
│   ├── widgets/
│   ├── features/
│   └── shared-ui/
│
├── application/
│   ├── anime/
│   ├── user-list/
│   ├── authentication/
│   └── ports/
│
├── domain/
│   ├── anime/
│   ├── user/
│   └── user-list/
│
├── synchronization/
│   ├── user-list/
│   ├── revalidation/
│   └── conflict-resolution/
│
├── infrastructure/
│   ├── providers/
│   │   └── anilist/
│   │       ├── api/
│   │       ├── dto/
│   │       ├── mappers/
│   │       └── authentication/
│   ├── query/
│   ├── persistence/
│   └── authentication/
│
└── shared/
    ├── api/
    ├── lib/
    └── types/
```

Не создавайте пустые каталоги или абстракции «на будущее» без реального сценария. Структура показывает ожидаемые границы; наполнение должно оставаться минимальным и оправданным.

### 3.3. Граница между Presentation и Application

Внутри `presentation/` допустимо использовать организационные идеи FSD:

- `pages/` — композиция экранов, привязанных к маршрутам;
- `widgets/` — крупные самостоятельные блоки интерфейса;
- `features/` — UI и клиентская логика взаимодействия, относящиеся к конкретной пользовательской возможности;
- `shared-ui/` — переиспользуемые визуальные компоненты без бизнес-сценариев.

Это **не означает**, что `presentation/features/` должен содержать всю реализацию пользовательского сценария. Сценарий приложения и его orchestration находятся в `application/`. UI вызывает application use case или фасад, предоставленный Application Layer.

Не нужно механически переносить все привычные FSD-слои в каждый архитектурный слой. FSD-подобная организация применяется только там, где она помогает упорядочить UI.

## 4. Правила зависимостей

### 4.1. Базовое правило

Зависимости направляются от внешних механизмов к внутренним правилам. Domain не импортирует Application, Presentation, TanStack Query, IndexedDB, GraphQL-клиент или AniList DTO. Application определяет необходимые ему контракты, а инфраструктура реализует их.

При этом конкретный сценарий может использовать инфраструктурные реализации через явно собранные зависимости и предусмотренные интеграционные фасады. Не следует создавать скрытые импорты реализации из домена или маскировать зависимости случайными переэкспортами.

### 4.2. Таблица разрешённых зависимостей

| Откуда | Может зависеть от | Не должен напрямую зависеть от |
|---|---|---|
| `presentation/` | `application/` публичные API, `domain/` типы для отображения при необходимости, `shared-ui/`, общие UI-примитивы | AniList DTO/API, IndexedDB persister, низкоуровневые GraphQL-операции, детали конфликт-резолвинга |
| `application/` | `domain/`, собственные порты/контракты, типы сценариев | Конкретные реализации AniList, IndexedDB, browser storage, UI-компоненты |
| `domain/` | Другие доменные модули и чистые общие типы при необходимости | `application/`, `presentation/`, `infrastructure/`, TanStack Query, GraphQL, IndexedDB, AniList |
| `synchronization/` | `application/` контракты, `domain/`, необходимые query/sync-порты | UI-компоненты, прямое управление произвольными компонентами интерфейса |
| `infrastructure/providers/` | `application/` порты, `domain/` модели, общий транспорт | `presentation/` |
| `infrastructure/query/` | TanStack Query и адаптеры/контракты, необходимые для интеграции с Application и Synchronization | Доменные правила как место для хранения query lifecycle |
| `infrastructure/persistence/` | TanStack Query persister API, IndexedDB и политика персистентности | `domain/` как владелец хранилища, UI-компоненты |
| `infrastructure/authentication/` | Внешние OAuth-механизмы, инфраструктурные настройки и application-контракты | Доменная модель как место для хранения токенов |
| `app/` | Публичные API слоёв, wiring и конкретные реализации инфраструктуры | Случайная бизнес-логика, дублирующая `application/` |
| `shared/` | Только общие низкоуровневые зависимости без обратных ссылок на конкретные feature/domain-модули | Импорты из `presentation/`, `application/`, `domain/` или `infrastructure/` в целях повторного использования |

Таблица задаёт целевое направление зависимостей. В случае необходимости конкретной связи её нужно выразить через контракт или интеграционный адаптер, а не нарушать правило прямым импортом.

### 4.3. Принцип портов и адаптеров

Если Application нуждается в получении данных, изменении списка или выполнении другой операции, Application описывает требуемый контракт (порт) в терминах приложения. Инфраструктурный адаптер реализует этот контракт с помощью AniList или другого технического механизма.

Не каждый вызов функции требует отдельного интерфейса. Порт нужен там, где он фиксирует существенную границу, позволяет заменить реализацию, изолирует внешний сервис или делает сценарий независимым от инфраструктуры.

**Не вводить абстракции ради абстракций:** один интерфейс на каждый файл, функция или простой внутренний вызов не требуется.

## 5. Ответственность слоёв

### 5.1. Presentation

Отвечает за:

- страницы, навигацию, UI и композицию компонентов;
- состояние, непосредственно необходимое для взаимодействия с интерфейсом;
- сбор пользовательского ввода и отображение результатов/ошибок;
- вызов сценариев Application через их публичные API.

Не отвечает за:

- правила домена;
- построение AniList GraphQL-запросов;
- преобразование provider DTO во внутреннюю модель;
- политику синхронизации и разрешения конфликтов;
- самостоятельное управление persistence.

Presentation может использовать React hooks для подключения UI к application/query-фасадам, но такие hooks не должны превращать Presentation в место реализации всей прикладной логики.

### 5.2. Application

Отвечает за:

- пользовательские сценарии (use cases);
- координацию действий между доменом и необходимыми портами;
- входные и выходные модели сценариев;
- контракты, выражающие потребности приложения во внешних возможностях;
- отделение сценария от конкретного провайдера.

Application не должен знать форму AniList DTO или детали GraphQL. Он работает с внутренними моделями и контрактами.

Примеры сценариев:

- найти аниме по пользовательскому запросу;
- получить детали аниме;
- получить список пользователя;
- изменить статус аниме в списке;
- начать/завершить сценарий аутентификации;
- запросить синхронизацию пользовательского списка.

Это примеры именования ответственности, а не требование создать отдельный класс на каждый пункт. Use case может быть функцией, объектом или другим простым механизмом, подходящим кодовой базе.

### 5.3. Domain

Отвечает за:

- внутреннюю модель приложения;
- доменные типы и допустимые значения;
- правила, относящиеся к аниме, пользователю и пользовательскому списку;
- инварианты и преобразования, которые являются правилами самого приложения.

Domain не должен содержать:

- provider DTO;
- AniList GraphQL operations;
- HTTP/GraphQL transport;
- React hooks;
- TanStack Query keys и query options;
- IndexedDB/persister;
- OAuth access token или browser-specific storage.

Доменные типы не должны быть копией внешнего API. Их форма определяется потребностями приложения и должна оставаться стабильной при смене провайдера.

### 5.4. Synchronization

Отвечает за координацию процессов синхронизации, повторной проверки актуальности данных и разрешения конфликтов в соответствии с архитектурными требованиями.

Synchronization **не является владельцем runtime query cache**. Жизненный цикл query state, кэширование, дедупликация запросов, retry и query invalidation относятся к TanStack Query и интеграционному слою вокруг него.

Если синхронизация инициирует обновление данных, она делает это через определённые контракты и механизмы, не реализуя параллельно собственный query cache.

Для MVP не нужно создавать сложный synchronization framework без подтверждённого сценария. Но если сценарий синхронизации/конфликтов появляется, его ответственность должна быть локализована именно здесь, а не растворена между UI hooks и provider adapter.

### 5.5. Provider Integration

Отвечает за:

- интеграцию с AniList и будущими провайдерами;
- GraphQL operations, provider-specific запросы и DTO;
- преобразование внешних ответов во внутренние модели;
- преобразование команд приложения в формат внешнего API;
- изоляцию особенностей статусов и других понятий провайдера;
- provider-specific OAuth-механизмы, если они технически связаны с конкретным провайдером.

Внешний DTO не должен выходить за границу адаптера и становиться публичной моделью Domain/Application/Presentation.

Для добавления нового провайдера предпочтительно реализовать новый адаптер под существующие контракты приложения, а не добавлять проверки `if (provider === ...)` в доменные сущности или UI.

### 5.6. Query Cache

TanStack Query / QueryClient — владелец runtime query cache и жизненного цикла server state.

К этой ответственности относятся:

- query keys и конфигурация запросов;
- кэширование и дедупликация;
- stale/retry/refetch политика в рамках принятых решений;
- mutation lifecycle и invalidation;
- интеграция с persistence persister.

Query Cache не является доменной моделью, долговременной базой данных приложения или владельцем бизнес-правил. Query keys не должны становиться идентификаторами доменных сущностей вне своей инфраструктурной задачи.

Пользовательские query keys должны включать стабильный user ID там, где данные принадлежат конкретному пользователю. При logout нужно очищать или изолировать пользовательские данные согласно ADR-004/ADR-005.

### 5.7. Persistence

Отвечает за долговременное сохранение только разрешённых категорий query state через принятый механизм — IndexedDB и TanStack Query persister в MVP.

Persistence не должен:

- создавать второй runtime cache параллельно QueryClient;
- становиться самодельной универсальной базой данных приложения;
- хранить OAuth token в query cache;
- самостоятельно определять доменные правила;
- сохранять все запросы без учёта категории и политики.

Политика сохранения должна быть явной, проверяемой и согласованной с ADR-005. Изменение политики persistence — архитектурное изменение, а не случайная настройка в UI hook.

### 5.8. Authentication

Аутентификация имеет несколько аспектов, которые нельзя смешивать в одном произвольном модуле:

- UI сценария входа/выхода находится в Presentation;
- сценарий и публичный контракт аутентификации относятся к Application;
- провайдерские OAuth URL, token exchange и особенности AniList относятся к Provider Integration/Infrastructure;
- безопасное обращение с токеном и его runtime-хранение отделены от query cache.

OAuth token не является частью доменной модели аниме или пользовательского списка и не должен сохраняться как query data.

---

## 6. Data flow: поиск аниме

Ниже приведён пример направления вызовов. Конкретная реализация может отличаться деталями, но не должна нарушать границы ответственности.

1. Пользователь вводит поисковый запрос в Presentation.
2. UI обращается к публичному сценарию поиска в Application.
3. Application формирует запрос в терминах приложения и использует определённый порт.
4. Query integration/TanStack Query проверяет состояние запроса в runtime cache и управляет его жизненным циклом.
5. При необходимости получить данные вызывается provider adapter AniList через контракт.
6. Adapter отправляет GraphQL-запрос, принимает provider DTO и преобразует результат во внутреннюю модель.
7. Результат возвращается в контур Application/query integration и становится query state.
8. Presentation отображает внутреннюю модель, не завися от формы AniList ответа.
9. Persistence сохраняет результат только если категория данных и политика persistence это разрешают. По ADR-005 поисковые результаты по умолчанию не сохраняются.

Ключевой инвариант: Presentation и Domain не должны импортировать AniList DTO или GraphQL operation напрямую.

---

## 7. Data flow: изменение пользовательского списка

1. Пользователь инициирует изменение статуса аниме в Presentation.
2. Presentation вызывает application use case изменения списка.
3. Application проверяет и применяет правила приложения, используя Domain и необходимые контракты.
4. Query/mutation integration управляет состоянием операции, ошибками и соответствующей инвалидацией/обновлением query state.
5. Provider adapter переводит команду в AniList-специфичный запрос и преобразует ответ во внутреннюю модель.
6. При необходимости Synchronization координирует актуализацию данных, revalidation и разрешение конфликтов.
7. QueryClient остаётся единственным владельцем runtime query cache.
8. Persistence сохраняет данные пользовательского списка согласно политике ADR-005 и с учётом пользовательского контекста.
9. При logout данные пользователя должны быть очищены или изолированы в соответствии с принятыми правилами.

Не следует реализовывать этот сценарий как UI hook, который самостоятельно содержит GraphQL mutation, маппинг AniList статусов, правила предметной области, политику конфликтов и детали persistence. Это несколько разных ответственностей.

---

## 8. Query Cache и Persistence: чёткое разделение

Эти понятия связаны, но не взаимозаменяемы.

| Вопрос | Ответственный компонент |
|---|---|
| Где данные находятся во время работы приложения? | TanStack Query / QueryClient |
| Когда запрос считается stale и когда его повторить? | Политика TanStack Query и query integration |
| Как именовать запросы и изолировать данные пользователей? | Query integration / query keys |
| Какие query data разрешено сохранять? | Политика persistence |
| Как записать и восстановить разрешённый query state? | Persister / IndexedDB integration |
| Какие поля и статусы существуют в модели приложения? | Domain |
| Как AniList представляет эти поля и статусы? | Provider Integration |

Persistence — механизм сохранения части query state, а не отдельный владелец актуального состояния приложения. Synchronization может координировать revalidation, но не заменяет QueryClient.

---

## 9. Правила размещения кода

Используйте следующие вопросы в указанном порядке.

1. **Это UI, навигация или реакция на пользовательский ввод?** Разместить в `presentation/`.
2. **Это завершённый пользовательский сценарий или координация действий приложения?** Разместить в `application/`.
3. **Это внутреннее понятие или правило, которое не должно зависеть от API/хранилища?** Разместить в `domain/`.
4. **Это координация синхронизации, revalidation или разрешения конфликтов?** Разместить в `synchronization/`.
5. **Это код, знающий формат AniList, GraphQL operation, provider DTO или OAuth-поведение провайдера?** Разместить в `infrastructure/providers/anilist/`.
6. **Это жизненный цикл query cache?** Разместить в `infrastructure/query/`.
7. **Это IndexedDB, persister или политика сохранения query state?** Разместить в `infrastructure/persistence/`.
8. **Это техническая сборка зависимостей и bootstrap приложения?** Разместить в `app/`.
9. **Это действительно общий низкоуровневый примитив, не принадлежащий конкретному слою?** Только тогда рассматривать `shared/`.

Если код одновременно подходит нескольким пунктам, это часто означает, что в одном модуле смешано несколько ответственностей. По возможности разделите orchestration, provider-specific детали и UI.

### Примеры размещения

| Код | Место |
|---|---|
| `Anime` и внутренние типы статуса | `domain/anime/`, `domain/user-list/` |
| `SearchAnime` use case | `application/anime/` |
| Контракт получения аниме | `application/ports/` или рядом со сценарием, если он локален |
| AniList GraphQL query и DTO поиска | `infrastructure/providers/anilist/` |
| Маппинг AniList Anime DTO → `Anime` | `infrastructure/providers/anilist/mappers/` |
| Query keys/options для поиска | `infrastructure/query/` или presentation-facing query integration, но не в Domain |
| UI поисковой строки и карточек результатов | `presentation/features/` и `presentation/widgets/` |
| React Router route/page | `presentation/pages/` и/или `app/routing/` в зависимости от принятой схемы маршрутизации |
| IndexedDB persister | `infrastructure/persistence/` |
| OAuth redirect/token exchange AniList | `infrastructure/providers/anilist/authentication/` |
| Сценарий входа/выхода | `application/authentication/` |
| Экран кнопки входа | `presentation/features/` |
| Логика разрешения конфликта синхронизации | `synchronization/` |

## 10. Как обращаться с React hooks и TanStack Query

React hooks не обязаны быть целиком сосредоточены в одном каталоге. Их расположение определяется ответственностью.

- UI hooks для состояния компонентов могут находиться в Presentation.
- Hooks, адаптирующие query/mutation к UI, могут быть тонким фасадом в Presentation, если это удобно React-компонентам.
- Query keys, общие query options, cache lifecycle и интеграция с persister должны иметь явного инфраструктурного владельца.
- Provider-specific HTTP/GraphQL вызовы и DTO должны оставаться в Provider Integration.
- Доменные правила не должны прятаться в React hooks.
- Если hook выполняет весь сценарий — GraphQL, mapping, доменные проверки, invalidation и synchronization — его необходимо разделить.

Не следует строить искусственную многоэтажную цепочку обёрток для каждого запроса. Цель — ясные границы, а не максимальное количество файлов.

## 11. Правила для ИИ-агентов

Следующие правила являются обязательными для любых изменений, выполняемых ИИ-агентом.

### 11.1. Перед изменением

1. Прочитать этот документ и определить, какие архитектурные границы затрагиваются.
2. Проверить существующие модули и соглашения, прежде чем создавать новый каталог или абстракцию.
3. Для решений, затрагивающих SAD/ADR, сверить изменение с соответствующим документом.
4. Если требования документов конфликтуют или недостаточны для решения, явно обозначить неопределённость и запросить уточнение, а не молча изобретать правило.

### 11.2. При реализации

1. Не импортировать AniList DTO/API из `domain/` или напрямую из `presentation/`.
2. Не помещать provider-specific маппинг в Domain.
3. Не размещать бизнес-сценарии в UI-компонентах или в низкоуровневом provider adapter.
4. Не переносить ответственность QueryClient за runtime cache в Synchronization.
5. Не реализовывать отдельный runtime cache или самодельную базу данных параллельно принятым механизмам без отдельного архитектурного решения.
6. Не сохранять OAuth token в query cache.
7. Соблюдать пользовательскую изоляцию query keys и очистку пользовательских данных при logout.
8. Не помещать код в `shared/` только ради удобства импорта.
9. Не создавать интерфейсы и классы для каждой функции. Вводить порт или адаптер, когда он защищает реальную границу.
10. Не добавлять новую архитектурную систему поверх уже выбранной без явного согласования.

### 11.3. После реализации

Проверить:

- соответствие ответственности выбранному слою;
- направление импортов и отсутствие циклических зависимостей;
- отсутствие provider DTO за границей Provider Integration;
- соответствие query/persistence политике;
- изоляцию данных пользователя;
- обработку ошибок и отмены запроса там, где это требуется;
- тесты на сценарий и mapping, если они уместны;
- typecheck, lint и тесты, если проектные инструменты доступны.

Если техническая проверка не была запущена или недоступна, агент обязан сообщить об этом прямо и не утверждать, что изменение проверено.

## 12. Как применять архитектуру к текущему MVP

Не требуется одномоментно переписывать приложение. Переносить существующий код следует постепенно, сохраняя работающие сценарии.

Рекомендуемый порядок:

1. **Зафиксировать структуру и правила зависимостей** в этом документе.
2. **Вынести AniList-specific API, DTO и mapping из Domain/Entity-модулей** в `infrastructure/providers/anilist/`.
3. **Определить внутренние модели и контракты Application**, чтобы внешние DTO не протекали в остальные слои.
4. **Провести один сквозной сценарий — поиск аниме** через Presentation → Application → Provider Integration → внутреннюю модель → Query Cache.
5. **Провести второй сценарий — изменение пользовательского списка**, уточнив границы Application, Query integration и Synchronization.
6. **Проверить persistence и logout**, включая пользовательскую изоляцию.
7. Только после проверки этих сценариев переносить остальные модули по той же схеме.

Порядок нужен, чтобы проверить, что архитектура действительно помогает проекту, до массовых перемещений файлов.

---

## 13. Эволюция от MVP к BFF/SSR

Цель — сохранить внутренние контракты, а не гарантировать неизменность каждого файла.

При переходе к BFF/SSR могут измениться:

- место выполнения Application use cases;
- расположение Provider Integration;
- место и механизм доступа к persistence;
- часть orchestration и authentication infrastructure;
- способ доставки данных в Presentation.

При этом должны по возможности сохраниться:

- внутренняя Domain Model;
- смысл Application use cases и их контрактов;
- provider-agnostic подход;
- граница Provider Integration;
- явное разделение Synchronization и Query Cache;
- правила пользовательской изоляции и безопасности токенов.

Клиентский TanStack Query cache и IndexedDB persistence могут остаться на клиенте даже при появлении BFF, если это будет соответствовать будущей архитектуре. Не следует заранее утверждать, что все текущие инфраструктурные компоненты обязательно переедут на сервер: это будет отдельное решение на основании будущих требований.

---

## 14. Что не является целью

Данная архитектура **не** требует:

- использовать FSD во всём приложении;
- создавать отдельный класс/use case для каждой функции;
- создавать интерфейс для каждого модуля;
- вводить сложный DI-контейнер;
- дублировать TanStack Query собственным кэшем;
- создавать отдельную базу данных приложения вместо принятого persistence-механизма;
- строить полноценный offline-first режим в рамках MVP;
- заранее реализовывать сложную синхронизацию или конфликт-резолвинг без соответствующего сценария;
- физически переносить код на сервер до появления требований к BFF/SSR.

Архитектура должна быть достаточно явной, чтобы границы было легко понять, и достаточно простой, чтобы не замедлять разработку MVP.

---

## 15. Критерии соблюдения архитектуры

Изменение соответствует этому документу, если:

- [ ] Domain не зависит от провайдера, React, QueryClient и persistence.
- [ ] Application описывает сценарии и необходимые контракты в терминах приложения.
- [ ] Provider Integration изолирует AniList API, DTO, OAuth-детали и mapping.
- [ ] Presentation отвечает за UI и вызывает сценарии через публичные API.
- [ ] Synchronization не владеет runtime query cache.
- [ ] TanStack Query / QueryClient остаётся владельцем runtime server-state cache.
- [ ] Persistence сохраняет только разрешённые категории query state.
- [ ] OAuth token не сохраняется в query cache.
- [ ] Пользовательские данные изолированы по стабильному user ID, а logout обрабатывает пользовательский кэш согласно политике.
- [ ] `shared/` не используется как произвольное место для кода без владельца.
- [ ] Архитектура не вводит ненужные абстракции и не копирует один и тот же сценарий в нескольких слоях.
- [ ] При реализации не нарушается возможность дальнейшего перехода к BFF/SSR без ненужной зависимости Domain/Application от текущей клиентской инфраструктуры.

---

## 16. Итоговое решение

Для MyAnimeList используется **модульная Clean/Hexagonal Architecture с явными границами Presentation, Application, Domain, Synchronization и Infrastructure**. Внутри Presentation можно применять организационные идеи FSD для страниц, виджетов и UI-возможностей, но FSD не определяет архитектуру всего приложения.

Это решение сохраняет смысл границ, зафиксированных в SAD и ADR, делает направление зависимостей видимым в структуре каталогов и уменьшает необходимость каждый раз мысленно раскладывать архитектурные компоненты по чужим слоям.

Если потребуется изменить эти правила, изменение следует оформить как осознанное архитектурное решение и согласовать с SAD/соответствующими ADR, а не вводить его случайно в ходе реализации.
