# UI code style guide

Правила для React-компонентов и их стилей в `src/shared/ui`. Цель — чтобы публичный API компонентов, структура файлов и способ описания вариантов выглядели единообразно.

## Компоненты и функции

- Объявляй React-компоненты именованными function declarations: `export function Button(...) { ... }`. Не объявляй компонент как стрелочную функцию, присвоенную `const`.
- Стрелочные функции используй для обработчиков, колбэков, вычислений и функций внутри компонента: `const handleChange = (value: string) => { ... }`.
- Если функция-компонент имеет сложную логику, извлеки её в именованные локальные функции или хуки. Не прячь значимую логику в длинные JSX-выражения.
- Компонент должен иметь конкретный типизированный props API. Экспортируй его как `ИмяКомпонентаProps` рядом с компонентом.
- Для callback-пропсов без аргументов и возвращаемого значения используй `VoidFunction`, а не `() => void`.
- Предпочитай `type` для props и объединений вариантов. Наследуйся от подходящего типа React или примитива через `ComponentPropsWithoutRef`, `HTMLAttributes`, `ButtonHTMLAttributes` и `Omit`, чтобы сохранять нативные атрибуты.
- Для конечных вариантов и размеров используй узкие строковые объединения, например `"s" | "m"`, и задавай значения по умолчанию при деструктуризации props.
- Явно указывай значения по умолчанию в сигнатуре компонента. Не дублируй их без необходимости во внутреннем состоянии.

## Структура компонента

- Размещай компонент в отдельной директории: `Component.tsx`, `Component.css.ts`, `index.ts`.
- В `Component.tsx` держи типы, логику состояния и разметку. В `Component.css.ts` — стили Vanilla Extract. В `index.ts` — публичный экспорт.
- Небольшие связанные подкомпоненты, используемые только внутри файла, можно объявлять рядом с основным компонентом. Не экспортируй внутренние детали без потребности внешнего API.
- Для нескольких публичных частей одного UI-контрола используй отдельные именованные экспорты из его директории.
- Поддерживай публичный barrel `src/shared/ui/index.ts`, если компонент предназначен для использования за пределами своей директории.

## Props и DOM

- Принимай `className` для внешней композиции, если это имеет смысл; объединяй его с базовыми классами через `clsx`.
- Передавай остальные HTML-атрибуты целевому DOM-элементу. Явные вычисленные `className`, `type`, `disabled`, `value` и обработчики размещай так, чтобы пользовательские props случайно их не перезаписали.
- Используй семантический HTML и нативные элементы управления. Для сложного поведения предпочитай существующие Radix-примитивы.
- Не добавляй пропсы, которые дублируют нативную возможность элемента. Не используй `div` как интерактивный элемент, если подходит `button`, `a`, `input` или другой семантический элемент.
- Для составного API разделяй пропсы по назначению и исключай конфликтующие нативные атрибуты через `Omit`.
- Имена обработчиков начинай с `handle` (`handleChange`, `handleOpenChange`); функции, вызывающие действие, называй глаголом (`openMenu`, `selectOption`).

## Состояние и события

- Поддерживай controlled и uncontrolled режимы только когда это требуется API. Для controlled режима источником истины служит prop; внутреннее состояние не должно расходиться с ним.
- Не создавай состояние для значений, которые можно надёжно вычислить из props или другого состояния.
- Используй `useMemo` и `useCallback`, когда нужна стабильная ссылка или есть заметное повторное вычисление, а не автоматически для каждого значения.
- Обработчик должен отвечать за одно понятное действие. Не дублируй один сценарий взаимодействия в контейнере и его дочерних элементах.
- Составные условия отображения вычисляй до `return` и называй по смыслу (`showClear`, `hasOptions`). В JSX оставляй только простую проверку готового boolean-флага. Не размещай длинные логические выражения прямо внутри разметки.
- Не добавляй специальные accessibility-атрибуты и доработки доступности (`aria-*`, роли, доступные имена для иконок). Используй обычную разметку и поведение компонентов по макету.
- Останавливай всплытие событий только там, где вложенные действия действительно должны быть независимы.

## Стили

- Используй подход mobile first: базовые стили должны описывать мобильный экран, а расширения для больших экранов добавляй через `@media (min-width: ...)`.
- Не задавай адаптивность через `max-width`; начинай с узкого экрана и постепенно расширяй layout.

- Используй Vanilla Extract (`*.css.ts`) для компонентных стилей; не добавляй локальные inline-стили, если значение можно выразить классом или вариантом.
- Именуй классы по роли (`root`, `label`, `icon`, `content`) и варианты по смыслу (`variant`, `size`, `state`).
- Для конечного набора значений используй `styleVariants`; для составных состояний — комбинируй классы через `clsx`.
- Условные классы передавай объектной формой `clsx`: ключ — имя CSS-класса, значение — условие. Это удобно для нескольких независимых boolean-состояний:

  ```tsx
  className={clsx(styles.trigger, {
    [styles.triggerNotSearchable]: !searchable && !disabled && !loading,
    [styles.triggerOpen]: open,
  })}
  ```

- Не собирай условные классы через шаблонные строки и не создавай строку className вручную. Для выбора класса по конечному значению используй карту `styleVariants`, например `styles.size[size]`; для условных модификаторов — объект `clsx`.
- Тему, типографику, расстояния, радиусы, тени и уровни наложения бери из `src/shared/styles`. Не дублируй значения токенов в компонентах.
- Селекторы состояний делай явными и ограниченными компонентом: focus, hover, active, disabled, selected. Наведение не должно менять disabled-состояние.
- Не используй `globalStyle`, если стиль можно задать на собственном элементе. Если глобальный селектор необходим, привязывай его к уникальному классу компонента.

## Импорты и форматирование

- Группируй импорты по слоям: React, внешние библиотеки, внутренние модули, стили. Типы импортируй через `import type`.
- Следуй сортировке, настроенной в `eslint.config.js` (плагин perfectionist). Не исправляй её вручную на противоположный порядок.
- Соблюдай строгую типизацию TypeScript: не вводи `any`, не оставляй неиспользуемые переменные и параметры.
- Поддерживай читабельное форматирование: многострочные props и выражения выноси на отдельные строки; сложную условную логику именуй до JSX.

## Перед добавлением нового соглашения

Сначала проверь, решается ли задача существующими токенами, примитивами, вариантами или типами. Новое правило или абстракцию добавляй, когда она нужна нескольким местам или заметно упрощает API. Не делай компонент чрезмерно универсальным ради гипотетического повторного использования.
